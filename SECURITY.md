# Security Policy

Engineering Bridge V1 (v1.5.0) is a local supervised bridge that connects an MCP client to local Codex and DSH executors. It is designed for one trusted local operator: treat the MCP client and the workspace configuration as trusted local inputs, and do not expose the process as a remote service. It is not a hardened remote service for untrusted callers.

## Current enforced controls

- The server uses local STDIO and exposes 15 tools: `run_task`, `task_result`, `control_task`, `bind_project`, `create_project`, `authorize_workspace_write`, `generate_controlled_patch`, `refine_controlled_patch`, `submit_controlled_patch`, `apply_controlled_patch`, `commit_controlled_patch`, `configure_validation_profile`, `validate_controlled_patch`, `start_controlled_patch_validation`, and `get_controlled_patch_validation`.
- Ordinary `run_task` execution is always read-only, with an optional `executor: "codex" | "dsh"` (default `codex`). Successful interactive turns enter `waiting_for_supervisor_review`; `task_result` exposes state/readiness, bounded evidence, and pre-acceptance `review_output`, then final `output` or `error` after finalization. For interactive tasks, `control_task` state-checks `continue`, `steer`, `interrupt`, and `accept`; continue preserves native Codex thread continuity and interrupt applies only while running and ends failed. Running generated/refined proposal tasks also accept interrupt (and Codex proposals accept steer), but not continue or accept. DSH has no machine-resumable headless session, so DSH `continue` starts a new execution and no thread id is ever fabricated.
- Workspace IDs and roots come from a startup configuration file. Manual registrations must be absolute and normalized, duplicate IDs are rejected, and MCP callers cannot modify manual registrations. Managed onboarding is confined to configured `project_root` approved roots and requires exact `BIND`/`CREATE` confirmation; canonical real paths are compared, so paths must resolve inside an approved root.
- Managed workspaces are registered read-only by default. `authorize_workspace_write` grants controlled-write permission to a managed workspace only, after exact `AUTHORIZE` confirmation, and never modifies a manual registration.
- Codex runs through `codex app-server --stdio` with approval `never`, a read-only sandbox, network disabled, and the configured workspace as its working directory. Instructions use the app-server STDIO protocol; the bridge does not invoke a shell or accept caller-supplied executable paths or process arguments.
- DSH runs through the official headless interface. The bridge pins `DSH_PERMISSION_MODE=read-only` for every DSH process, so a host permission override cannot widen it, and forwards only an explicit environment allowlist (including `DEEPSEEK_API_KEY` and `DSH_TOOLS_MODE`); proxy and other secret-like variables are not forwarded.
- The Codex and DSH children receive small allowlists of inherited environment fields.
- Returned execution failures use fixed error codes and messages rather than forwarding executor stderr or raw internal errors. `partial_output` appears only when a genuine interrupt produced real partial output; the task still ends `failed`, and ordinary failures never re-expose stderr or partial stdout.
- Codex evidence is bounded (string length, changes count, and total entry count). When these existing bounds truncate or evict evidence, explicit markers (`[truncated]`, changes-omitted counts, an evidence-drop item) are returned so the supervisor knows the diagnostic information is incomplete. Markers are not a security guarantee and are not a complete transcript.
- Workspace writes default to disabled. `generate_controlled_patch`, `refine_controlled_patch`, and `submit_controlled_patch` are read-only proposal flows available in any registered workspace; they require no write authorization. They verify a clean Git top-level (with an existing HEAD, or unborn-repository support for added-file proposals) and record or require the exact `base_head`. Submitted proposals run no executor and record submitted provenance. Proposal tasks never enter supervisor review or expose `review_output`; running generated/refined tasks may be interrupted (and Codex tasks steered), but proposals cannot be accepted through `control_task`.
- Executor runs have a 15-minute hard deadline and bounded TERM-to-KILL shutdown. Active Codex turns also have a two-minute watchdog reset only by notifications carrying the exact active `threadId` and `turnId`; RPC responses and global or mismatched notifications cannot reset it. Short Codex RPC calls have a separate 30-second bound, and controlled-patch/onboarding Git subprocesses have a 60-second bound.
- After human review outside task state, application requires the completed proposal task, controlled-write permission (managed `AUTHORIZE` or a manual `allow_write: true` entry), and exact `APPLY` confirmation, then rechecks root, HEAD, and clean tracked worktree/index state. It permits modifications to existing tracked regular files and additions of absent ordinary text files only with exact mode 100644 and matching `/dev/null` headers. It rejects deletions, binary patches, mode changes, executable additions, symlinks, submodules, rename/copy, unsafe paths, duplicate paths, and new targets present in HEAD, the index, or the worktree. Fixed no-shell `git apply --check` and `git apply` calls receive the patch on standard input; application is once only and never runs tests, stages, commits, or pushes.
- A separate exact `COMMIT` gate stages the retained patch content exactly and creates one commit without pushing. It rejects a nonempty index and unrelated tracked dirt; stable unrelated untracked recovery anchors are fingerprinted and preserved without being staged. If final recovery-anchor verification fails after Git created the commit, Bridge fails closed without resetting or rewriting history.
- Controlled-patch validation is opt-in and on-demand: only an explicit synchronous `validate_controlled_patch` or asynchronous `start_controlled_patch_validation` call runs validation. Existing task, proposal, and apply paths gain no automatic validation or tests, and there is no background validation queue. Both validation paths reuse the existing controlled-patch preflight and apply candidate changes only in a temporary detached Git worktree at the proposal base HEAD, with 600-second default per-step and 1200-second total budgets. Results are `PASS`, `FAIL`, or `INCOMPLETE`; an unborn-base proposal is `INCOMPLETE` with reason `unsupported_unborn_base`.
- Executable validation comes only from the trusted configured profile. Each registered workspace has at most one fixed validation profile, persisted in the Bridge-local `<config>.validation-profiles.json` sidecar with mode 0600 and replaced only as a whole after exact `CONFIGURE` confirmation (never `AUTHORIZE`). Configured commands are non-empty argv arrays executed with `shell: false`. Synchronous `validate_controlled_patch` accepts only `patch_task_id` and waits for its report. Async `start_controlled_patch_validation` accepts only `patch_task_id` and `idempotency_key`; callers cannot inject commands, argv, shell text, a profile, or timeouts.
- Async start durably admits the run with proposal/profile identity frozen at admission and returns its `validation_run_id` without waiting for validation to complete. Execution is service-owned; caller disconnect does not cancel the run while Bridge remains alive. `get_controlled_patch_validation` accepts only `validation_run_id` and reads bounded retained state and results; it never executes, retries, resumes, cleans up, changes state, or waits for validation.
- Async process supervision covers only the direct supervised child and its POSIX process group; it does not govern arbitrary daemonized descendants or descendants that escape the group via `setsid`. Windows returns `VALIDATION_PLATFORM_UNSUPPORTED` for async validation. Normal worktree cleanup requires verified ownership and confirmed termination of the supervised child/process group. Bridge restart does not resume, retry, attach to, or signal an interrupted run's old processes, and does not visit or automatically clean up stale worktrees. In the current implementation, startup converts interrupted non-terminal runs to `INCOMPLETE`; retained terminal results remain queryable without execution. Hard crashes can leave children or stale state requiring later explicit controlled recovery; deleting paths does not clear `recovery_required`.
- Three local state files provide restart persistence, written atomically with mode 0600: `<config>.managed-workspaces.json` (the managed workspace catalog), `<config>.controlled-patches.json` (controlled-patch proposals and applied history), and `<config>.validation-profiles.json` (the fixed per-workspace validation profiles). Invalid managed-catalog records are skipped individually; invalid retained controlled-patch records are quarantined without blocking startup, while replay/applied ambiguity and global invariants still fail closed. These files are not a credential store and not a complete audit log.
- Async validation records use a separate private `<config>.validation-runs/` store with atomic mode-0600 records and single service ownership. Persistence failure is fail-closed: it blocks further admission and notifies the service to abort active validation. Keep validation configuration and state outside repositories, registered workspaces, and approved onboarding roots.

## Current limitations

The bridge does not authenticate MCP callers. It has no HTTP or remote transport, resource quota, or persistent task/thread/evidence supervision history: active task supervision state (tasks, threads, evidence, review outputs) is process-local and disappears on restart, even though controlled-patch proposals, the managed workspace catalog, validation profiles, and async validation results persist. Read-only tasks do not verify that configured paths are Git repositories (the controlled-patch flows do). Configured manual workspace roots are canonicalized when resolvable and their canonical identity is refreshed before relevant root lookup and managed registration. This root-identity canonicalization does not by itself provide a general symlink-containment guarantee for arbitrary descendant paths. The trusted local operator must therefore control the configuration file, choose workspace roots carefully, and control which local MCP client can start and use the server.

Codex's read-only sandbox and DSH's pinned read-only permission prevent writes, but Engineering Bridge does not provide filesystem read isolation. Executors running as the same operating-system user may still read files outside the configured workspace that the user already has permission to read, so use it only on trusted machines and with trusted local clients.

Temporary-worktree validation protects the registered workspace from candidate patches and build artifacts, but it is not a host-level sandbox: configured validation commands run with the operating-system permissions of the Bridge user and remain subject to that user's host access boundary. Configure validation profiles only for trusted workspaces and only with commands the trusted operator fully trusts. Validation does not change proposal or task lifecycle state. `PASS` never authorizes `APPLY`, and async validation never automatically performs `APPLY`, `COMMIT`, or `PUSH`.

The read-only execution boundary is an execution control, not a guarantee that prompts or returned text contain no sensitive data. Do not place credentials or secrets in instructions, configuration, or public bug reports.

## Reporting a vulnerability

Do not publish secrets, credentials, private prompts, source code, or personal data in an issue. After the repository is hosted and its security-advisory feature is available, use that feature for private vulnerability reports. Until then, omit sensitive details from public reports.
